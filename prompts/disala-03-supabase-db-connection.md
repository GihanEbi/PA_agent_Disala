## Architectural decisions

1. **ORM: Prisma**, per `AGENTS.md` §6, connected to Supabase's managed Postgres.
2. **Auth stays on Clerk.** Supabase Auth is not enabled or used. The `User` table links to Clerk via a unique `clerkId` column instead of Supabase's `auth.users`.
3. **Authorization is enforced at the application layer**, not via Supabase RLS + `anon`/`authenticated` roles — because the app talks to Postgres directly through Prisma (not through Supabase's Data API/PostgREST). Every query will be scoped by the internal `userId` resolved from the Clerk session in server-side code.
   - RLS will still be **enabled on every table** in `public` as defense-in-depth, with **no policies granted to `anon`/`authenticated`** (we don't use the Data API). The connection Prisma uses is the default `postgres` role, which has `bypassrls`, so this doesn't block the app.
   - `supabase db advisors` (via MCP) will be run after migrating to confirm no lint warnings.
4. **Connection strings**: Supavisor **transaction pooler** (port 6543, `?pgbouncer=true`) for `DATABASE_URL` (serverless-friendly, used at runtime), and the **direct connection** (port 5432) for `DIRECT_URL` (used only by `prisma migrate`). This is Supabase's current documented pattern for serverless Next.js deployments.
5. **No `supabase-js` client for now.** Nothing in this step needs Supabase's Data API, Storage, or Realtime — Prisma alone covers DB access. `supabase-js` can be added later if a feature needs those specifically.
6. **Token encryption deferred.** `ConnectedAccount.accessToken`/`refreshToken` are modeled as `String` columns intended to hold ciphertext (per `AGENTS.md` §15/§16), but the actual encrypt/decrypt implementation is out of scope here — no real provider tokens exist yet since no OAuth integration is wired up. This will be addressed in the Gmail/Calendar connection prompt.
7. **No custom Postgres role.** Supabase's Prisma guide suggests creating a dedicated `prisma` DB role via SQL Editor; skipping that for now as unnecessary complexity for a single-user project — using the default `postgres` role with the provided password.
