# Disala — Backend Phase 4: Conversational agent, real chat, and approval-gated Gmail/Calendar actions

## Goal

Tie Phases 1–3 together into the thing `AGENTS.md` actually describes as the product: a real conversation with Disala, backed by a real LLM agent that calls the Phase 3 tool layer, persisted as real `Conversation`/`Message` rows, with consequential actions (sending an email, creating a calendar event) going through a real, persisted `Approval` object that the user must explicitly approve before anything is ever written to their Gmail or Calendar.

Concretely, this phase ships:

1. An OpenAI-backed agent (per your explicit request to use your OpenAI key) that understands intent, calls Phase 3's Gmail/Calendar/Notes functions as structured tools, and replies in natural language — per `AGENTS.md` §14's read-tool diagram.
2. Real `Conversation`/`Message` persistence — nothing has ever written to either table before this phase.
3. A real `Approval` object lifecycle: created when the agent wants to send an email or create a calendar event, approved/rejected by the user, and — only on approval — actually executed against Google's real APIs for the first time in this project's history.
4. The two new Google-write functions that execution needs (`gmail.sendEmail`, `calendar.createEvent`) — the write calls Phase 3 deliberately never built.
5. A real chat surface: the existing, currently-inert "Ask Disala" voice sheet becomes a working text conversation (composer, transcript, approval cards) — the follow-up both `prompts/disala-05-native-notes.md` and `prompts/disala-06-gmail-calendar-tools.md` explicitly deferred to "once the AI agent exists."

### Explicitly split out of this phase (see "Should this be split further?" below)

This is already the largest phase so far. After inspecting everything, I split it — this prompt is the foundational slice; a follow-up Phase 5 prompt should cover:
- `calendar.updateEvent` / `calendar.cancelEvent` "prepare" + execution, and their `Approval` payload shapes (`disala-06`'s decision #2 explicitly deferred designing these until an approval system existed to protect them — it now does, but scoping that design work into *this* phase on top of everything else here is how a phase stops being reviewable).
- The dedicated `/approvals` page from `AGENTS.md` §18 (history, filters by status/type/date/service). This phase gives you the first-class `Approval` *object* and renders pending/resolved cards inline in the conversation that created them (satisfies §7.4 and Test 2), but not a standalone browsing UI.
- Proactive/unprompted suggestions, the `Suggestion` model, notifications, and the `reminders.*` tools (`AGENTS.md` §12, §17) — these need a scheduler/background-job trigger to fire *without* a user message, which is genuinely different infrastructure from "answer the message the user just sent," and no phase has built a job runner yet.
- Wiring the still-static `/`, `/mail`, `/calendar` pages (and the home page's hardcoded `INSIGHTS` array) to live tool data — a real task, but a UI-plumbing one, independent of whether the agent exists. The chat surface becomes the first place live Gmail/Calendar/Notes data is actually visible; the dashboard pages stay exactly as static as Phase 3 left them.
- Voice input (speech-to-text). The voice sheet's mic button stays exactly as inert as Phase 2 left it — this phase only makes the **keyboard/text** path real. Real speech is a separate integration decision (Whisper API, Realtime API, or the browser's own `SpeechRecognition`) nobody has asked for yet.

## Relevant skills

No packaged skill exists for the OpenAI API or the Vercel AI SDK, so the package choice, current tool-calling shape, and current streaming conventions below were verified live during this session (WebFetch against the SDKs' own docs, not recalled from training data — training data is stale here almost by definition, since both SDKs ship breaking changes on a roughly-yearly major-version cadence):
- `https://ai-sdk.dev/docs/foundations/tools` (fetched live) — confirms the current `tool()` shape is `{ description, inputSchema, execute }`; the parameter is **`inputSchema`**, not the older `parameters`. Page header marks **v7 as the AI SDK's current latest major**.
- `https://ai-sdk.dev/docs/agents/loop-control` (fetched live) — confirms multi-step tool-calling loops are controlled via `stopWhen` (e.g. a step-count condition), not the older `maxSteps`/`maxToolRoundtrips`. **Flagging an unresolved discrepancy honestly rather than guessing**: one fetch named the helper `isStepCount(n)`, a separate search result named it `stepCountIs(n)` — these are different names for what's evidently the same concept, and I can't tell from documentation alone which is currently correct (possibly one is aspirational/pre-release docs, or naming changed between minor versions). This must be confirmed against whatever version `npm install ai` actually resolves at implementation time (check the package's own type definitions/exports) before writing the agent loop — not guessed.
- `https://ai-sdk.dev/docs/getting-started/nextjs-app-router` (fetched live) — current streaming pattern is a Route Handler calling `streamText(...)` and returning `result.toUIMessageStreamResponse()`, consumed client-side by `useChat` from `@ai-sdk/react`. Cited here because it directly informed the streaming-vs-not decision below, even though this phase deliberately doesn't adopt it yet.
- Re-verified directly via `npm view` (this review pass, not the original drafting session — the first pass's cited version had gone stale/was wrong): current versions are `ai@7.0.93`, `@ai-sdk/openai@4.0.60`, `@ai-sdk/react@4.0.96`. - `https://developers.openai.com/api/docs/models` (fetched live, official OpenAI docs, not a third-party blog) — confirms the current model lineup and that function/tool calling is supported across the current flagship line. Model choice justified under "Architectural decisions" below.

## Architectural decisions

1. **Agent framework: Vercel AI SDK (`ai` + `@ai-sdk/openai`), not the raw `openai` npm package.** `AGENTS.md` §4 lists "AI SDK / LLM integration" and "Tool/function calling" as relevant skill areas and, in the same spirit as its OAuth guidance, favors a well-trodden SDK over a hand-rolled agentic loop. The AI SDK's `tool({ description, inputSchema, execute })` helper (confirmed live, see citations above) takes a Zod schema directly — Phase 3's tools already validate their own input with Zod, so this is a thin wrapper, not a second validation system. `@ai-sdk/openai`'s model provider talks to OpenAI's API directly; there's no reason to *also* add the plain `openai` SDK as a dependency — that would be two overlapping ways to call the same provider for no benefit.
2. **Model: `gpt-5.6-terra`.** Confirmed live against `developers.openai.com/api/docs/models`: OpenAI's current lineup (as of this session) is GPT-6 Astra (flagship) → GPT-5.6 Sol → GPT-5.6 Terra → GPT-5.6 Luna, all four supporting function/tool calling, with Terra and Luna both at a 1.05M-token context window. Disala's agent work — reading a handful of emails/events, drafting a reply, deciding priorities — doesn't need Astra/Sol's top-end reasoning tier, but a personal assistant that drafts emails and summarizes a user's actual mail on their behalf benefits from noticeably better judgment/writing quality than the cheapest tier; Luna is the better choice once real usage volume/cost data exists, but Terra is the more defensible default for a brand-new feature nobody has load-tested yet. Only our own tools are passed to it — OpenAI's own built-in web search / file search / computer-use tool types (also listed as available on Terra) are never enabled, because `AGENTS.md` §5/§14 require every external action to go through Disala's own controlled tool layer, not a provider-native browsing/computer-use tool operating outside it.
3. **Non-streaming for this phase — `generateText`, not `streamText`/`useChat`.** This is the one place I deliberately don't adopt what the research above found to be the current idiomatic pattern, for reasons specific to this phase, not a rejection of the pattern generally:
   - An approval card is a structured, all-or-nothing UI element (see `AGENTS.md` §19's own example: recipient/subject/message body, Approve/Reject) — it has nothing useful to render until the `propose_email`/`propose_meeting` tool call has *fully* resolved. Token-by-token streaming's main benefit (perceived latency on long prose) doesn't help the part of this feature that actually matters most (the first real external side effects this project has ever had) and adds real complexity (partial tool-call state, a stream that can be interrupted mid-write) to exactly the code path that most needs to be simple and correct.
   - `useChat`'s default transport sends the client's own accumulated message list back to the server on every turn. That's fine for display, but it is the wrong thing to trust as *model context* — a client could otherwise inject a fabricated prior "assistant" turn (e.g. one falsely claiming a still-pending approval was already sent) into what gets fed back to the model. Avoiding that means overriding `useChat`'s request-body construction, and I could not pin down with confidence which current AI SDK option name does that (see the `stopWhen` naming caveat above — this SDK's surface is moving fast); rather than guess at an unverified API and build message-integrity around it, this phase's server derives all model context itself from its own database (see decision #6) and the client never gets to supply conversation history at all.
   - Net effect: `app/api/chat/route.ts` is one ordinary `async POST` handler — request in, `generateText(...)` awaited, structured JSON response out — consistent with every other mutation in this codebase being a plain Server Action/async handler, not this codebase's first streaming client. Switching to `streamText` + `useChat` once this is proven working end-to-end is the natural, recommended next step, not a dead end — nothing about the tool layer, the Approval model, or the persistence shape below needs to change to add it later.
4. **Agent loop: `generateText` with `tools` and a bounded `stopWhen` step count (an exact-but-unconfirmed-name step-count condition, per the caveat above — verify against the installed package before writing this).** This is the AI SDK's documented "agent" pattern (a `generateText`/`streamText` call with tools enabled and a step budget above 1 — the model reasons, calls a tool, observes the result, reasons again). A cap (I'd suggest 8 steps) bounds both latency and OpenAI cost per user turn against a single runaway loop; it is not a rate limit against repeated abusive turns (see Assumptions — no such limit exists yet).
5. **Tool layer wraps Phase 3's functions; it does not replace them.** Every agent tool's `execute` is a thin adapter: parse/pass the model's arguments into the existing `lib/integrations/gmail.ts` / `lib/integrations/calendar.ts` / `lib/notes.ts` function, translate its `GoogleApiResult`/plain-array return into whatever the model needs to see (including the `ok:false` failure case — the model gets told a search failed, it never gets told nothing about it and left to hallucinate a result). **`userId` is never a tool parameter the model can set.** Every tool is built by a `buildAgentTools(userId, conversationId)` factory called once per request, after `userId` is resolved server-side from the authenticated session (`getOrCreateInternalUser()`) — the returned tool closures capture `userId`/`conversationId` from that call, and the Zod `inputSchema` the model actually sees never includes a `userId`/`conversationId` field at all. This is the direct, load-bearing implementation of `AGENTS.md` §14's "the model must never be given unrestricted access to external credentials" for this phase specifically — the model never sees a token, a `userId`, or anything to inject in place of one.
6. **Read tools answer directly; two specific tools ("propose" tools) create an `Approval` instead of acting.** Concretely, 8 tools:
   - `search_emails`, `get_email` → `gmail.searchEmails`/`getEmail` (read, no approval — `AGENTS.md` §7.3's own "generally low-risk" list).
   - `get_calendar_events`, `find_available_times` → `calendar.getEvents`/`findAvailableTimes` (read, no approval).
   - `search_notes` → `notes.searchNotes` (read, no approval).
   - `create_note` → `notes.createNote`, called **directly, no approval** — this isn't a new decision, it's `prompts/disala-05-native-notes.md`'s decision #7 (creating your own note isn't a consequential external action) extended to the agent creating it on your explicit request instead of you typing it yourself; the request itself ("take a note that...") is the user's own instruction, same as typing it into the composer. `ApprovalActionType.NOTE_CREATE`/`NOTE_UPDATE` remain defined in the schema (for future flexibility) but genuinely unused by this phase — an explicit gap, not a silent one, same style as `disala-06`'s undocumented-then-documented Calendar update/cancel gap.
   - `propose_email` → calls `gmail.createDraft` (unchanged), then **creates an `Approval`** (`actionType: EMAIL_SEND`, `payload` = the exact `DraftPayload` `createDraft` returned) and returns a `{ approvalId, status: "pending_approval" }`-shaped result to the model — not a "sent" confirmation, because nothing was sent. Covers both a brand-new email and a reply (`createDraft` already accepts optional `inReplyToMessageId`/`threadId`) — one tool, not two, since the underlying shape is identical.
   - `propose_meeting` → calls `calendar.prepareEvent` (unchanged), then **creates an `Approval`** (`actionType: CALENDAR_CREATE`, `payload` = the exact `EventPayload` returned), same "pending_approval" result shape. `CALENDAR_UPDATE`/`CALENDAR_CANCEL` have no corresponding tool — out of scope, see split above.
   - This is the direct implementation of `AGENTS.md` §14's action diagram (`Gather info → Prepare action → Create Approval → [stop — wait for the user]`) as a hard code-level boundary, not just a documented intention: nothing in `propose_email`/`propose_meeting`'s `execute` function calls a Gmail/Calendar write endpoint, at all, ever. The write only happens later, from the approve Server Action, in a completely different request.
7. **`Approval.title`/`.description` are templated from structured fields, not freely LLM-authored; the actual email body / event summary the user is approving is shown verbatim from `payload`.** E.g. title `"Send email to sarah@..."`, description `"Disala prepared this based on your conversation."` — factual scaffolding, not a place for the model to editorialize about its own action. This mirrors `AGENTS.md` §15's "distinguish known information from AI suggestions": the *fact* that an email is being proposed is structural; the *content* of that email (genuinely LLM-authored) is shown as data, in its own field, not blended into a description the model wrote about itself.
8. **Two new write functions, added to Phase 3's own integration files — not a new file, not a raw `googleapis` call from the route handler.** This directly answers the question `disala-06` left open: `AGENTS.md` §5 says provider-specific logic belongs isolated behind its own integration layer, and `lib/integrations/gmail.ts`/`calendar.ts` are already that layer for exactly this provider. Re-reading Phase 3's own code (not just its prompt) confirms the fit: `getAuthorizedGoogleClients`/`runGoogleApiCall` in `lib/integrations/google-client.ts` were written as fully generic helpers (`fn: () => Promise<{data: T}>`) even though, until now, only read calls used them — nothing about them is read-only, they were simply unexercised on the write path. Adding `sendEmail`/`createEvent` to the same two files, calling the same two helpers, is completing the module Phase 3 already shaped for this, not opening new surface area:
   - `gmail.ts` gains `sendEmail(userId, input)` — Zod schema `{ raw: z.string().min(1), threadId: z.string().optional() }` (deliberately *not* re-validating `to`/`subject`/`bodyText` — those were already fully validated when `createDraft` built `raw`; re-parsing a MIME string to re-derive them would be pure ceremony). Calls `gmail.users.messages.send({ userId: "me", requestBody: { raw, threadId } })` through `runGoogleApiCall`.
   - `calendar.ts` gains `createEvent(userId, input)` — Zod schema matching `EventPayload`'s exact shape (re-validated here because, unlike the MIME case, this payload sat in a `Json` column and lost its static type on the way — validating on the way back out is cheap insurance against a malformed row). Calls `calendar.events.insert({ calendarId: "primary", requestBody: { summary, description, start, end, attendees }, sendUpdates })` through `runGoogleApiCall`.
   - Both return the same `GoogleApiResult<T>` envelope Phase 3 established — no new error-handling shape invented for the one part of this codebase where getting error handling right matters most.
9. **New `Approval.result Json?` column** (schema migration). The existing model has no field to record *what happened* — `AGENTS.md` §16's audit-trail example ("Result: Gmail message ID xxx") needs somewhere to live that isn't `payload` (which must stay the original request, unmodified, for the record). `result` holds `{ messageId }` on a successful send, `{ eventId, htmlLink }` on a successful event creation, or `{ error: { code, message } }` on failure — populated by the execution step, never by the propose tools.
10. **Approval execution is a single atomic claim-then-call, inside the approve Server Action — no queue, no background job.** Concretely: `updateMany({ where: { id, userId, status: "PENDING", OR: [{expiresAt: null}, {expiresAt: {gt: now}}] }, data: { status: "APPROVED", approvedAt: now } })`. If this updates zero rows, the approval was already resolved (approved/rejected elsewhere) or has expired or doesn't belong to this user — the action returns the approval's *current* state and does **not** call Google, which is the entire idempotency guarantee for "user double-clicks Approve" or a retried request (`AGENTS.md` §15): Google is only ever called once per row, because only the request that wins the atomic claim is allowed to call it. Only after a successful claim does the action call `sendEmail`/`createEvent` and then write `status: "EXECUTED"`/`"FAILED"` + `result` + `executedAt`.
    - **Known, explicitly-flagged gap**: if the process crashes between the claim (`APPROVED`) and the final `EXECUTED`/`FAILED` write, that row is stuck at `APPROVED` with no code path to retry or resolve it (its `status` is no longer `PENDING`, so the claim query above can never match it again). This is a real gap, not silently solved — a future reconciliation job (or a manual DB fix) is the honest answer, same as `disala-06` flagged the unresolved Clerk empty-array-vs-throw question rather than pretending it away.
11. **`Approval.expiresAt` defaults to 24 hours from creation**, for both `EMAIL_SEND` and `CALENDAR_CREATE`. `AGENTS.md` §7.4 requires the field to exist and says the approval policy "should be configurable as the product evolves" — this phase picks one constant (long enough that a user who doesn't open the app same-minute isn't punished; short enough that a stale, no-longer-relevant proposal doesn't linger indefinitely) rather than building a configuration surface nobody has asked for yet. Approving an expired `PENDING` row: the pre-check (before attempting the atomic claim) finds `expiresAt < now`, flips it to `EXPIRED`, and tells the user plainly it expired — it does not execute.
12. **One continuous `Conversation` per user, not a conversation list/switcher.** `getOrCreateActiveConversation(userId)` returns the user's single most-recently-updated `Conversation` or creates one. `AGENTS.md`'s `Conversation.title` field exists in the schema for a future multi-thread UI, but nothing in `AGENTS.md` §19–20's examples shows a conversation switcher — the whole product framing is "one ongoing assistant," closer to a single running chat than a ChatGPT-style sidebar. Building that switcher now, with no design reference for it (`AGENTS.md` §3: no UI is designed here without a reference image), would be speculative UI. This can change later without touching the `Conversation`/`Message` schema at all.
13. **Model context comes from the server's own persisted history, capped, not from the client.** The route handler loads the conversation's last 20 messages (`listRecentMessages`, newest-N, restored to chronological order) and builds the AI SDK's model-message array from those DB rows itself — never from anything the client sends beyond the new message's own text. This both closes the integrity gap in decision #3 and is a direct, literal implementation of `AGENTS.md` §13's "targeted retrieval... do not retrieve entire conversation history" instinct applied to cost/context-window control, not just to Gmail/Calendar. Everything past the last 20 messages is still stored (nothing is deleted) — just not sent to the model. If this cap becomes a real problem (a user with a very long-running relationship with Disala), summarizing older turns is future work, not attempted here.
14. **One `Message` row per turn, not one row per tool-call step.** A user's turn is one `Message` (`role: USER`). The agent's turn — however many tool calls it took internally to get there — is persisted as exactly one `Message` (`role: ASSISTANT`, `content` = the model's final natural-language text, `toolCalls` = a JSON summary of every tool call/result in that turn). `MessageRole.TOOL`/`.SYSTEM` remain defined in the schema but genuinely unused by this phase (the system prompt is rebuilt fresh per request from live data — current time, user name — so persisting it as conversation content would be actively wrong, not just unused). This matches the schema's own shape better than exploding into N rows: `toolCalls: Json?` sits on the *same* row as `content`, reading as "the assistant message that happened to involve these tool calls," not as a parallel timeline of tool events.
15. **Chat surface: the existing voice sheet becomes the real (text-only) conversation UI**, not a new page/route. This is the entry point both `disala-05` and `disala-06` pointed at ("this is explicitly the intended entry point for real conversation... once the AI agent exists"), it's already mounted globally (`VoiceSheetProvider` in `app/layout.tsx`), and — per the "Existing code inspected" note above — it already keeps its own state alive across close/reopen within a page load, which is exactly the property a chat needs. The sheet gains a second visual mode: tapping the (now-functional) keyboard button swaps the orb+suggestion-chips view for a scrollable transcript (`VoiceResponseCard` for assistant replies, a new plain right-aligned bubble for the user's own messages, a new `ApprovalCard` for pending/resolved approvals) plus a real text input at the bottom. The mic button and orb view are untouched and stay exactly as inert as before.
16. **New `app/actions/approvals.ts` (`"use server"`) for approve/reject — a small, deliberate departure from the existing `app/<page>/actions.ts` convention.** Every existing Server Action file (`app/notes/actions.ts`, `app/settings/connections/actions.ts`) is colocated with, and calls `revalidatePath` on, the one page that owns it. Approval cards render inside the globally-mounted voice sheet, not under any one route — there is no single page to colocate with or revalidate (the sheet's own client state is updated directly from the action's return value, not via a server-driven re-render). A new `app/actions/` directory for actions that belong to a cross-cutting UI surface rather than one page is a small, legible convention, not a one-off inconsistency — future cross-cutting actions (if any) have an obvious home.

## Assumptions

- **Conversation history is not rehydrated into the chat UI on a fresh page load.** The sheet's transcript starts empty each time the page is loaded (not each time the sheet is opened/closed — see decision #15), even though the DB still holds everything. Seeding `useState` from `listRecentMessages` on mount is straightforward future work; leaving it out keeps this phase's client-side surface to "one `fetch` call per turn," which matters given how much server-side surface (agent, tools, approvals, two new write functions) this phase already adds.
- **No per-user rate limiting on `app/api/chat/route.ts` beyond the per-turn `stopWhen` step cap.** Nothing in this codebase does request rate-limiting today; adding it generically is out of scope here, but a chat endpoint that spends real OpenAI-API money per call is the first place in this project where that gap has a direct cost, not just a security cost — flagging it as a recommended near-term follow-up, not solving it now.
- **`User.timezone` (schema default `"UTC"`) is read as-is for "what time is it for this user" in the system prompt.** No phase has ever built a way for a user to actually set their real timezone — it will read `"UTC"` for every user until one does. Dates like "tomorrow at 3 PM" will resolve correctly relative to UTC, which is silently wrong for a user elsewhere; this is a real, pre-existing gap this phase inherits and surfaces rather than fixes (fixing it means a settings UI, which is its own small phase).
- **Approve/reject/execute happens synchronously inside the Server Action request** — no queue, no background retry. Gmail/Calendar single-call latency is normally sub-few-seconds, so the user's browser waiting on the button click is acceptable for now; a background job would only matter at a scale this product isn't at yet.
- **No re-check of calendar availability at execution time.** `propose_meeting`'s `find_available_times` check (if the model makes it, per the system prompt's instruction — not programmatically enforced) reflects availability *at proposal time*; if real time passes before the user approves, the slot could theoretically no longer be free by the time `createEvent` runs. Google's own `events.insert` doesn't reject on a conflict by default, so this phase doesn't detect that case — noted as a real, small gap, not solved here.
- **The chat endpoint and its tools operate on the same single Google connection Phase 1 modeled** — nothing about multiple mailboxes/calendars changes here.
- **No new environment variables beyond `OPENAI_API_KEY`.**

## Functional requirements

- Opening the voice sheet and tapping the keyboard button reveals a text input; sending a message shows it in the transcript immediately, followed by Disala's real reply once the request completes (no fabricated/instant "typing" reply — `VoiceStateChip` may show a lightweight "Thinking…" state while the request is in flight).
- Asking "what important emails did I get today" produces a reply grounded in real `search_emails`/`get_email` results from the signed-in user's actual connected Gmail account — never invented senders/subjects.
- Asking "what does my afternoon look like" produces a reply grounded in real `get_calendar_events` results.
- Asking "reply to \<sender\> and say \<content\>" (given enough context in the conversation to identify which email) results in a rendered `ApprovalCard` (`EMAIL_SEND`) showing the exact recipient/subject/body Disala prepared — and **no Gmail API call has happened yet**.
- Approving that card sends the real email via Gmail, the card updates to reflect success, and the real Gmail account's Sent folder contains it.
- Rejecting a card marks it `REJECTED` and no Gmail/Calendar call is ever made for it.
- Asking to schedule a meeting with enough detail (who, when, how long) produces an `ApprovalCard` (`CALENDAR_CREATE`); approving it creates a real event on the connected Google Calendar; the card reflects the real result (including a link to the event, when Calendar returns one).
- Asking to schedule a meeting **without** enough detail (e.g. "schedule a meeting with John," no time given) results in Disala asking a clarifying question in plain text — no tool call, no `Approval` created, matching `AGENTS.md` §15's "ambiguous requests" rule.
- Asking Disala to take a note creates a real `Note` row immediately, with **no** approval card, consistent with decision #6.
- Asking "prepare me for my meeting with \<person\> tomorrow" produces a reply that combines calendar, email, and notes context from actual tool calls into one summary (`AGENTS.md` §12's cross-service example) — achievable in this phase because it's ordinary same-turn multi-tool orchestration, not unprompted proactivity.
- Double-clicking Approve (or otherwise triggering the action twice) results in exactly one email sent / one event created, never two.
- Every `Message`/`Approval` row created by any of the above is scoped to the authenticated user who created it; a second signed-in test user never sees the first user's conversation, messages, or approvals.

## Security considerations

- `app/api/chat/route.ts` re-checks `auth()` server-side on every request; `userId` for every tool call and every persisted row comes from that session, never from anything in the request body.
- The model is never given a `userId` parameter to set, a Google access token, or any credential — every tool's `inputSchema` (what the model actually sees and can populate) omits `userId`/`conversationId` entirely (decision #5); it only ever calls Phase 3's already-scoped functions.
- `OPENAI_API_KEY` lives server-side only (`.env.local`, no `NEXT_PUBLIC_` prefix); `app/api/chat/route.ts` is the only place it's read, and it's never present in anything returned to the browser.
- Model context is built exclusively from the server's own DB-persisted history (decision #13) — the client-supplied request body is only ever `{ message: string }`, never a message array the server would trust as prior context.
- `approveApproval`/`rejectApproval` scope every query by `userId` (same pattern as `deleteNote`'s ownership-scoped `deleteMany`) — a user can never approve or reject another user's pending action, and the return value is `false`/a "not found" outcome, not a thrown error that could leak whether a given `approvalId` exists for someone else.
- No email/calendar content, and no OpenAI request/response body, is logged — failures log the error code/HTTP status only (same discipline `disala-06` established for the read tools, extended to the write path and to the OpenAI call itself).
- `sendEmail`/`createEvent` are reachable **only** from `approveApproval`'s post-claim step — there is no route, action, or tool that calls either function directly, so "the model decided to send an email" is not a code path that can exist no matter what the model outputs; only a user's own Approve click can trigger it.

## AI/agent behavior

- System prompt (rebuilt fresh per request, per decision #13) states: who Disala is and for whom; the current real date/time (ISO, in `user.timezone`) so relative dates resolve against a stated instant instead of a guess; that Disala must never claim an email was sent or an event was created — only that it was *prepared*, pending the user's approval, because `propose_email`/`propose_meeting` never send/create anything themselves; that ambiguous requests (missing recipient/date/time/duration) should be met with a clarifying question in plain text, not a guessed tool call; that only the information actually needed for the current request should be retrieved (no "just search everything" calls); and that a reply should clearly separate what a tool actually returned (fact) from what Disala is recommending (suggestion), per `AGENTS.md` §15.
- Read tools (`search_emails`, `get_email`, `get_calendar_events`, `find_available_times`, `search_notes`) return their result (or a structured failure — `GoogleApiResult`'s `ok:false` branch, translated into a plain object the model can read and explain honestly, e.g. "I couldn't check your calendar — your Google connection needs to be reconnected") directly into the agent's next reasoning step; nothing about a read tool waits for user approval.
- `create_note` executes immediately (no approval, per decision #6) and returns the created note's id/content back to the model to confirm.
- `propose_email`/`propose_meeting` never execute anything — they call the existing `createDraft`/`prepareEvent` (unchanged), persist an `Approval`, and return `{ approvalId, status: "pending_approval" }` to the model, which should then tell the user it prepared something and is waiting for approval (matching `AGENTS.md` §7's "I found a suitable time... I prepared the meeting invitation. Would you like me to send it?" example) — never "sent" or "created."
- The agent loop is bounded (`stopWhen`, decision #4) — if it hits the step cap without producing a final answer, the route handler still returns whatever partial text `generateText` produced rather than hanging or erroring, and logs that the cap was hit (a signal the cap or a tool might need tuning later, not something to silently ignore).

## Approval requirements

- `EMAIL_SEND` (from `propose_email`) and `CALENDAR_CREATE` (from `propose_meeting`) are the only two actions this phase can create an `Approval` for, and the only two this phase can execute. Both are exactly the `AGENTS.md` §7.3 "requires approval" examples ("sending an email," "creating a meeting invitation").
- `CALENDAR_UPDATE`/`CALENDAR_CANCEL` — no tool exists to create either, and `approveApproval`'s execution dispatch has no branch for either `actionType`; if one somehow existed as a row (it can't, from this phase's own code), approving it would be a no-op with no execution path, not a silent wrong action. Building the real thing is the recommended Phase 5 work described at the top.
- `NOTE_CREATE`/`NOTE_UPDATE` — never created by this phase's tools (decision #6); creating your own note through the agent is not a consequential external action, same reasoning `disala-05` already established for the manual composer.
- Every approval card shows, per `AGENTS.md` §19's own worked example: what Disala wants to do (the action type, in plain language), why (the templated description), the exact data involved (the verbatim `payload` — recipient/subject/body, or summary/time/attendees), and Approve/Reject buttons. Once resolved, the same card shows the outcome (sent/created, or exactly why it failed) rather than disappearing or leaving the user to guess.

## Error handling

- Every Phase 3 tool's `ok:false` result is translated into a plain object the model receives as the tool's result (not a thrown error the agent loop has to recover from) — the model is expected to explain the failure honestly per the system prompt, never to claim the underlying read succeeded.
- If `generateText` itself throws (OpenAI API error, timeout, network failure), `app/api/chat/route.ts` catches it, does **not** persist a fabricated assistant message, and returns a plain error response the client renders as "Disala couldn't respond — try again" — the user's own message is still persisted (it was saved before the model call), so nothing the user typed is lost even if the reply fails.
- `sendEmail`/`createEvent` failures (any `GoogleApiResult` `ok:false`) result in `Approval.status = "FAILED"`, `result = { error: { code, message } }`, `executedAt` still set (an execution *attempt* happened, even though it failed) — the approve action's response tells the user plainly, e.g. "I couldn't send that email — Gmail rejected the request. Nothing was sent," per `AGENTS.md` §7.5's own worked example, never "Done!"
- Approving an already-resolved or expired approval returns that approval's actual current state (never re-attempts execution) with a message appropriate to that state ("This was already sent," "This request expired — ask me again if you'd still like to do this").
- Approving/rejecting an approval that doesn't belong to the caller (or doesn't exist) returns a generic "not found" outcome — never distinguishes "doesn't exist" from "isn't yours."
