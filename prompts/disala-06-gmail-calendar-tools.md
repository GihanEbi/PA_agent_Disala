# Disala — Backend Phase 3: Gmail + Calendar tool layer (read + prepare, no writes yet)

## Goal

Build the **tool layer** `AGENTS.md` §5/§14 describes for Gmail and Calendar: well-typed, Zod-validated, permission-checked, structured-output functions that a future AI agent (Phase 4) will call. This phase does not build the agent, the chat endpoint, the approval system, or any UI — it only makes it *possible* for those things to exist by giving them something real to call against a Google-connected user's live Gmail/Calendar data.

Concretely, this phase ships:

1. A shared Google API client helper that turns a signed-in user into an authorized Gmail/Calendar client, using the access token Clerk already manages (Phase 1), with structured, honest error handling.
2. Read-only Gmail tools: `searchEmails`, `getEmail` (with real MIME parsing — Gmail returns base64url-encoded multipart bodies, not plain text).
3. Read-only Calendar tools: `getEvents`, `findAvailableTimes` (via `freebusy.query`, matching the `calendar.freebusy` scope already granted for exactly this).
4. A "prepare" tool for each provider that produces a fully-formed, validated payload for a *consequential* action (a new email, a new calendar event) **without performing that action** — see Architectural decision #1, the central decision of this prompt.
5. `notes.searchNotes` — explicitly deferred to "the Gmail/Calendar/Notes tool-layer phase" by `prompts/disala-05-native-notes.md`; that's this phase.

Out of scope for this prompt:
- The AI agent, tool-calling loop, chat endpoint, and system prompt (Phase 4).
- The `Approval` model's execution step and any UI for it (Phase 4) — this prompt produces the payloads Phase 4's execution step will eventually send/insert, but does not send or insert anything itself.
- Any actual `gmail.users.messages.send`, `gmail.users.drafts.create`, `calendar.events.insert`, `calendar.events.patch`, or `calendar.events.delete` network call — see decision #1.
- Any UI. Nothing in `app/` or `components/` changes.
- Retry/backoff logic for rate limits — surfaced as a structured error, not handled with automatic retries yet.

## Relevant skills

- `supabase-postgres-best-practices` — for the `notes.searchNotes` Prisma query pattern (no schema change, so mostly not applicable this time).

No packaged skill exists for the Gmail API, Calendar API, or the `googleapis` Node client, so the request/response shapes and package choice below were verified live against Google's and npm's current docs/registry during this session (not recalled from training data — see citations inline):
- Gmail API: [`users.messages.get`](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get) (`format=full` vs `metadata` vs `raw`), [search/filter syntax](https://developers.google.com/workspace/gmail/api/guides/filtering) (`q` parameter: `is:unread`, `is:important`, `from:`, `after:`, `before:`, etc.), [creating drafts](https://developers.google.com/workspace/gmail/api/guides/drafts) (`{"message":{"raw": "<base64url RFC 2822>"}}`).
- Calendar API: [`freebusy.query`](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query) (`items: [{id}]` request, `calendars: {[id]: {busy: [{start,end}]}}` response), [`events.insert`](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert) (`summary`, `description`, `start`/`end` as `{dateTime, timeZone}`, `attendees: [{email}]`, `sendUpdates` query param: `all`/`externalOnly`/`none`).
- Package choice: confirmed live via `npm view` (this session) — `googleapis@178.0.0` (the full meta-package, bundles 200+ Google APIs), `@googleapis/gmail@18.0.0` and `@googleapis/calendar@16.0.0` (scoped single-API packages), `google-auth-library@11.0.2`. All four share `repository.url: googleapis/google-api-nodejs-client` — the scoped packages are the *same* official client generator output as the full `googleapis` package, just published per-API, not a third-party fork.
- Clerk: confirmed live (Clerk Backend SDK docs, this session) that `getUserOauthAccessToken(userId, provider)` takes the bare provider name (`'google'`, not `'oauth_google'`) and returns `Promise<PaginatedResourceResponse<OauthAccessToken[]>>`. **Not confirmed, and worth flagging honestly rather than guessing**: whether calling it for a provider the user never connected resolves with an empty `data` array or throws (Clerk's docs don't say either way, and a second documentation pass this session couldn't pin it down further). `getAuthorizedGoogleClients` must handle **both** possibilities defensively — wrap the call in try/catch *and* check `data.length === 0` inside the try — and this phase's manual test steps include actually observing which one happens against a real never-connected test user, so the implementation is verified empirically rather than assumed.

## Architectural decisions

1. **This phase performs zero write calls to Google's APIs — not even Gmail drafts.** This is the single most important decision here, so the reasoning gets its own numbered points:
   - `AGENTS.md` §14's own diagram for action requests is: `Gather information → Prepare action → Create Approval → User approves → Execute tool → Verify result → Respond`. "Execute tool" — the step that actually calls the provider — comes *after* `Create Approval`, which doesn't exist until Phase 4. Under a literal reading of that diagram, no tool call that changes anything on Google's side should exist in the codebase before the approval system does, full stop — not "except drafts, because drafts are private."
   - A tempting alternative was: let `gmail.createDraft` actually call `users.drafts.create`, since a Gmail draft is private (only the owner sees it) and reversible (can be deleted), so arguably not "consequential" under §7.3's definition. This was rejected because (a) it creates an asymmetry with Calendar, where there is no equivalent "private, inert" object — even a personal-calendar event risks `sendUpdates` reaching real attendees, so Calendar's write path can't use the same argument; treating Gmail and Calendar differently here would be an arbitrary line, not a principled one; (b) if a real Gmail draft is created now but the user never approves sending it (because Phase 4 doesn't exist yet to approve/reject it), it becomes an orphaned side effect this phase's own tests can't clean up or account for — the exact "stray automation the AI did on its own" outcome `AGENTS.md` §23 warns against; (c) it buys nothing functionally — Disala's approval *card* is the review surface the user actually sees (§7.4), not the user's own Gmail Drafts folder, so there is no product reason for a real Gmail draft to exist before the moment Phase 4 sends it.
   - So: `gmail.createDraft` and `calendar.prepareEvent` are **pure, local, validated functions**. They check the user has an active-looking Google connection (fast pre-check against the cached `ConnectedAccount`, so Disala doesn't offer to prepare a meeting invite for someone who obviously can't send one), validate and shape their input with Zod, and — for `createDraft` specifically — **fully build the real base64url-encoded RFC 2822 MIME message** now (see decision #3), because that MIME-construction work is genuine, testable logic this phase should own, and it's exactly what `users.drafts.create` or `users.messages.send` will need *verbatim* in Phase 4. Building it now and executing it later are cleanly separable; building it now and also executing it now are not.
   - Net effect: after this phase, the codebase has real, tested code paths that *read* live Gmail/Calendar data, and real, tested code that *shapes* a send/insert payload — but literally no function anywhere that can mutate a user's Gmail or Calendar. That is a strong, easy-to-state, easy-to-verify security property for this phase's acceptance criteria, and it's a strictly cleaner story than "most writes are deferred, except these specific ones we decided were fine."
2. **`calendar.updateEvent`/`calendar.cancelEvent` "prepare" helpers are not built in this phase at all**, not even as unused stubs. Unlike a new event (which needs real payload-shaping logic: validating `start`/`end`, timezones, attendees), an update or cancellation is fundamentally `{eventId, changes}` / `{eventId}` — there's no Gmail/Calendar-specific shape worth building ahead of time, and building it now would mean guessing at a schema for `Approval.payload` before Phase 4 defines how `ApprovalActionType.CALENDAR_UPDATE`/`CALENDAR_CANCEL` payloads are actually structured end-to-end. Phase 4 defines and validates those inline when it wires the approval payload schemas — cheaper and more accurate than this phase guessing now. Documented as an explicit gap, not silently dropped.
3. **Package choice: `@googleapis/gmail` + `@googleapis/calendar` + `google-auth-library`, not the full `googleapis` meta-package.** Confirmed live (npm registry, this session): `googleapis@178.0.0` bundles generated clients for every Google API Google publishes; `@googleapis/gmail@18.0.0` and `@googleapis/calendar@16.0.0` are the same generated client code, published per-API from the same `googleapis/google-api-nodejs-client` source repo. Since Disala only ever needs two of those APIs, the scoped packages avoid pulling ~200 unrelated API clients into `node_modules`/the build, with no loss of official support or type quality — this satisfies `AGENTS.md` §4's "follow the provider's official API documentation... prefer official SDKs over hand-rolled" without over-installing. `google-auth-library` is added as an explicit direct dependency (not left as a transitive resolution of the two scoped packages) because our own code imports `OAuth2Client` from it directly — an explicit dependency is the correct way to depend on code you import, regardless of what else happens to already pull it in.
   - **How the client is authorized**: `new OAuth2Client()` (no `clientId`/`clientSecret`/`redirectUri` — those are only needed for the authorization-code exchange or for automatic refresh, and Clerk already does both of those for us) then `.setCredentials({ access_token })` with the token from `getUserOauthAccessToken`. This client is only ever used for the single request it was built for and is never cached across requests/users (a fresh one is constructed per call in `lib/integrations/google-client.ts`) — it holds a live secret in memory for the shortest useful time.
4. **File layout: a new `lib/integrations/` subfolder, not flat `lib/*.ts`, and not a new top-level `/integrations` folder.** `AGENTS.md` §5 explicitly recommends isolating "provider-specific logic" behind its own integration layer (`/integrations/gmail`, `/integrations/calendar`) "to prevent provider-specific logic from spreading throughout the application" — that's a real, applicable concern now in a way it wasn't for `lib/google-oauth.ts` (a scope list) or `lib/connected-accounts.ts` (a thin sync/read-model), neither of which is a provider API *client*. This phase's `gmail.ts`/`calendar.ts` genuinely are provider API clients — real request-shaping, real response-parsing, real provider-specific error codes. Nesting them under `lib/integrations/` rather than a sibling top-level folder keeps "all server-side logic lives under `lib/`" true (the existing convention), while still giving Gmail/Calendar code its own clearly-bounded home the way `AGENTS.md` asks for. `lib/notes.ts` is *not* moved — Notes has no external provider to isolate from (native Postgres-backed per Phase 2's decision), so it stays exactly where it is; only `searchNotes` is added to it.
5. **A shared result envelope for every Gmail/Calendar tool function**: `Promise<GoogleApiResult<T>>` where `GoogleApiResult<T> = { ok: true; data: T } | { ok: false; error: { code: GoogleApiErrorCode; message: string } }`, defined once in `lib/integrations/google-client.ts`. Every failure mode this phase can produce — not connected, needs reauth, insufficient scope, rate limited, invalid input, unknown provider error — is a *value*, not a thrown exception. This directly serves `AGENTS.md` §7.5/§15 ("never claim success without verification," "explain failures clearly"): a future agent-tool wrapper (Phase 4) can render `ok: false` uniformly without a mix of try/catch and return-value checking, and it matches the precedent `lib/notes.ts#deleteNote` already set (return a structured outcome, don't throw, for an expected failure mode). `notes.searchNotes` does **not** use this envelope — it just returns `Note[]`, matching `listNotes`'s existing plain return type, because Notes has no external provider and therefore no distinct provider-failure taxonomy to encode; wrapping it in the same envelope as Gmail/Calendar would be needless ceremony for a query that can only meaningfully succeed or throw a real Prisma error.
6. **Input validation is Zod, applied inside each exported function, not at a separate "controller" layer** (there isn't one yet — no route or Server Action calls these directly in this phase). A failed `safeParse` is surfaced as `{ ok: false, error: { code: 'INVALID_INPUT', message } }` through the same envelope, not thrown — keeping the "one contract" property from decision #5 total, including for the one failure mode this phase's own tests will hit constantly (making sure Phase 4 can never send malformed provider requests, whatever it eventually validates on its own side).
7. **`getEmail`'s MIME parsing lives in its own module (`lib/integrations/gmail-mime.ts`)**, separate from `gmail.ts`'s API-calling code, and `createDraft`'s MIME *building* lives there too — decoding and encoding a MIME message are inverse operations over the same base64url/RFC 2822 domain, and keeping them together makes it obvious they should stay consistent (e.g., both need to agree on how `\r\n` line endings and header folding are handled). This mirrors Phase 2's `lib/format-timestamp.ts` split — a focused pure-function module pulled out of the feature module that uses it, not left inline.
8. **`searchEmails` never fetches full message bodies.** It calls `messages.list` (ids/threadIds only) then `messages.get` with `format: 'metadata', metadataHeaders: ['From', 'Subject', 'Date']` per result — enough to build a useful summary (sender, subject, date, snippet, `isUnread`/`isImportant` from `labelIds`) without paying the cost (quota and payload size) of parsing every matched message's full MIME body. Fetching one message's full content is what `getEmail` is for, called explicitly once the caller (eventually, the agent) decides a specific message matters — this is exactly `AGENTS.md` §13's "targeted retrieval" principle ("do not retrieve: entire Gmail mailbox") applied at the tool level, not just the agent-prompt level.
9. **"Important" and "unread" map to Gmail's own query operators**, not a heuristic Disala invents: `is:important` and `is:unread` (confirmed live in Gmail's search-syntax docs, this session) are appended to the `q` string built from `searchEmails`'s structured input, alongside `after:`/`before:` (Gmail's own date-range operators) and any free-text the caller passes through. Disala is not deciding what "important" means — Gmail's own importance markers are, matching `AGENTS.md` §15's "distinguish known information from AI suggestions."

## Assumptions

- **`searchEmails`/`getEvents` operate on `userId: 'me'` / `calendarId: 'primary'` only** — the authenticated Google account's own inbox and primary calendar. Multiple mailboxes/calendars per connection aren't something Phase 1 modeled and aren't in scope here.
- **`findAvailableTimes` defaults to querying only the user's own primary calendar** (`calendarIds` optional, defaults to `['primary']`) — checking a second person's availability (e.g., Sarah's) requires *her* calendar ID and her own consent to be queryable, which is a cross-user data-sharing question `AGENTS.md` doesn't resolve yet (§10's "If another person's availability is required, use the appropriate calendar information available to the user" is deliberately vague on how). Building for one calendar now, with the parameter already shaped to accept more, means Phase 4 can extend this without changing the function's contract once that policy exists.
- **No pagination beyond a capped `maxResults`.** `searchEmails`/`getEvents` accept a caller-supplied `maxResults` capped at 50 server-side (regardless of what's requested) — a personal-assistant "what emails did I get today" query has no business scanning thousands of messages, and an agent that needs more should narrow its query, not paginate through everything.
- **Time inputs are ISO 8601 strings** (`timeMin`/`timeMax`/`dateTime` etc.), validated by Zod's `.datetime()`, not `Date` objects — these functions' inputs will eventually come from an LLM's structured tool-call arguments (JSON), which can't carry a native `Date`.
- **Rate limits/quota are surfaced, not engineered around.** Gmail and Calendar both enforce per-project and per-user quota (unit costs vary by call, e.g. Gmail list/get calls cost a small number of quota units each against a large daily project budget, refreshed per 100-second windows) — exact current limits are configurable per Google Cloud project and are best checked in that project's own Cloud Console quota page rather than hardcoded here. This phase maps a `429`/quota-exceeded `403` to `error.code: 'RATE_LIMITED'` and stops there; automatic backoff/retry/queueing is real future work, not attempted now.
- **No new environment variables or secrets.** Access tokens flow through Clerk exactly as Phase 1 established; this phase adds no API keys of its own.

## Functional requirements

- `searchEmails({ query?, unreadOnly?, importantOnly?, after?, before?, maxResults? })` returns up to `maxResults` (capped 50, default 10) matching messages as `{ id, threadId, from, subject, date, snippet, isUnread, isImportant }[]`, newest first (Gmail's default `messages.list` order), scoped to the authenticated user's own mailbox only.
- `getEmail({ messageId })` returns `{ id, threadId, from, to, cc, subject, date, bodyText, isUnread, isImportant, labelIds }` with `bodyText` a clean, readable string (no raw base64, no leftover MIME boundary markers, no unstripped HTML tags when only an HTML part exists).
- `createDraft({ to, cc?, subject, bodyText, inReplyToMessageId?, threadId? })` returns `{ to, cc, subject, bodyText, threadId, raw }` where `raw` is a valid base64url-encoded RFC 2822 message (round-trips: decoding `raw` back to text reproduces the given headers/body) — and makes **no** Gmail API call.
- `getEvents({ timeMin, timeMax, maxResults? })` returns events in that window from the user's primary calendar as `{ id, summary, description, start, end, attendees, htmlLink, status }[]`, ordered by start time, `singleEvents: true` (recurring events expanded into instances, matching how a person actually reads "what's on my calendar today").
- `findAvailableTimes({ timeMin, timeMax, durationMinutes, calendarIds? })` returns `{ slots: {start, end}[], busy: {start, end}[] }`, where every returned slot is at least `durationMinutes` long and doesn't overlap any interval in `busy`.
- `prepareEvent({ summary, description?, start, end, attendees?, sendUpdates? })` returns the exact payload shape `events.insert` will need (validated: `end` after `start`, valid IANA `timeZone`, valid attendee emails) and makes **no** Calendar API call. Returns `{ok:false, error:{code:'NOT_CONNECTED'|'NEEDS_REAUTH', ...}}` if the cached `ConnectedAccount` shows no usable Google connection, so Disala doesn't prepare an invite it already knows it can't eventually send.
- `notes.searchNotes({ userId, query })` returns the signed-in user's own notes whose `title` or `content` contains `query` (case-insensitive), newest-updated first — never another user's notes, matching `listNotes`'s existing scoping.
- Every function above validates its input with Zod before doing anything else and never trusts a client-supplied `userId` — `userId` is always the caller's already-resolved internal user id, matching every existing `lib/*.ts` function's contract.

## Security considerations

- No Google access token is ever logged, returned to a caller, or persisted anywhere — `getAuthorizedGoogleClients` holds it in a local variable for the duration of one call and nothing in this phase writes it to the database (consistent with Phase 1: Clerk is the only place the real token lives).
- Every Gmail/Calendar call is scoped to `userId: 'me'`/`calendarId: 'primary'` for *that request's own* authorized client — there is no code path where one user's resolved client could be used to fetch another user's data, because the client is built fresh, per call, from that specific `internalUserId`'s own Clerk-issued token.
- `ConnectedAccount` cache reads are used only as a fast pre-check/UX nicety (decision/assumption above), never as the sole authorization gate — an attempt is only ever considered denied once Google's own API actually says so (401/403), or once we already know from the cache there is no connection at all worth attempting.
- Email/calendar content (subjects, bodies, attendee lists) is never logged — error paths log the error code/HTTP status only, never the request or response body, since both can contain personal message content.
- Zod schemas reject unexpected/oversized input (e.g. `bodyText` length caps, `maxResults` caps, array length caps on `attendees`/`to`/`cc`) before any provider call is attempted — defense against a future caller (agent) passing pathological input through to Google's API.

## Approval requirements

Not applicable to any function in this phase, but for a decision-specific reason per function, not a blanket exemption:

## Error handling

Every Gmail/Calendar function returns `{ ok: false, error: { code, message } }` (never throws for an expected failure) with `code` one of:
- `NOT_CONNECTED` — `getUserOauthAccessToken` returned an empty `data` array **or** threw (both are handled — see the Clerk caveat under "Relevant skills": which one actually happens isn't documented, so both paths lead here), or the cached `ConnectedAccount` is missing/`REVOKED` (fast pre-check).
- `NEEDS_REAUTH` — Google returned `401` (token invalid/revoked on Google's side despite Clerk thinking it had one). Also triggers `markGoogleConnectionNeedsReauth(internalUserId)` so the `/settings/connections` page (Phase 1) reflects reality on next load, without this phase adding any UI of its own.
- `INSUFFICIENT_SCOPE` — Google returned `403` with an `insufficientPermissions`/scope-related reason.
- `RATE_LIMITED` — Google returned `429`, or `403` with a quota-exceeded reason.
- `INVALID_INPUT` — the input failed Zod validation; message includes the first Zod issue's path/message, not the raw Zod error object.
- `PROVIDER_ERROR` — anything else Google's API rejects with (malformed request, `404` on an unknown `messageId`/`eventId`, network failure) — message is the provider's own error message where available, never fabricated.
- `deleteNote`'s existing "not found or not yours" boolean-return convention is preserved for `searchNotes` by construction (a query, not a mutation, so there's no analogous failure to report beyond "zero results").
- Nothing in this phase ever reports success without having actually received and checked a real Google API response — no function assumes a call worked because it didn't throw synchronously.

## Acceptance criteria

- `searchEmails`/`getEmail` against a real connected Gmail account return real messages matching what the Gmail web UI shows for the same search/message — no invented emails, no truncated-looking `bodyText` for a multipart HTML+plaintext message.
- `createDraft`'s `raw` output, decoded by hand (e.g. `Buffer.from(raw.replace(/-/g,'+').replace(/_/g,'/'), 'base64').toString()`), is a well-formed RFC 2822 message with the correct `To`/`Cc`/`Subject`/body — and, checked in the real Gmail account's Drafts folder, **nothing new appears there**.
- `getEvents`/`findAvailableTimes` against a real connected Calendar account return real events/gaps matching what the Google Calendar web UI shows for the same window — and `prepareEvent`'s output never results in a new event appearing on the real calendar.
- Revoking Google access from the Google Account's own "Third-party apps & services" page (same step Phase 1's manual tests used), then calling any Gmail/Calendar function, returns `{ok:false, error:{code:'NEEDS_REAUTH'}}` (not a thrown error, not a crash) and flips the `ConnectedAccount` row to `NEEDS_REAUTH` in Postgres.
- Calling any Gmail/Calendar function for a user who never connected Google returns `{ok:false, error:{code:'NOT_CONNECTED'}}` without ever attempting a network call to Google.
- `searchNotes` only ever returns notes owned by the calling `userId`, verified with two test users.
- `npm run lint`, `npx tsc --noEmit`, and `npm run build` all pass; `npx prisma validate` passes (no schema change expected, so this is a safety check, not a migration step).
- Grepping the repo for any of `messages.send`, `drafts.create`, `events.insert`, `events.patch`, `events.delete` finds **zero** call sites — only their names appearing in comments/documentation explaining why they're deferred.
